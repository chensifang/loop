# 请详细描述从 setNeedsDisplay 被调用，到像素点真正显示在屏幕上的全过程

## 核心概念

从调用 `setNeedsDisplay` 到像素显示在屏幕上，是一个复杂的渲染流程，涉及应用层、系统层、GPU 和硬件显示。整个过程是异步的，不会立即执行。

> **重要提示：** 只有当你覆写了 `drawRect:` 方法时，系统才会走 CPU 绘制流程。绝大多数情况下（如设置 `backgroundColor` 或 `UIImageView` 加载图片），是不走 `drawRect:` 的。一旦覆写 `drawRect:`，系统会为该 View 申请一块巨大的内存（寄宿图 Backing Store），其大小 = width × height × contentsScale² × 4 字节，这是极其耗费内存的。

## 完整流程时间线

| 时间点 | 阶段/操作 | 执行位置 | 详细解释 | 白话理解 |
|--------|----------|---------|---------|---------|
| **T0** | **调用 setNeedsDisplay** | App 进程（主线程） | 在视图的 `layer` 上设置 `needsDisplay` 标志位，标记这个视图需要重绘。标记会向上传播到父视图。**关键点：** `setNeedsDisplay` 是异步的，不会立即调用 `drawRect:`，只是标记需要重绘。**重要：** 只有当你覆写了 `drawRect:` 方法时，系统才会走 CPU 绘制流程。 | 就像在墙上贴了一张"需要重新粉刷"的便利贴，但还没开始刷墙。 |
| **T1** | **RunLoop 循环处理** | App 进程（主线程） | RunLoop 在每次循环中处理各种事件和更新，检查是否有视图被标记为 `needsLayout` 或 `needsDisplay`。 | 主线程是一个忙碌的工人，一直在处理各种任务，一边检查有没有需要更新的视图。 |
| **T2** | **RunLoop BeforeWaiting Observer** | App 进程（主线程） | RunLoop 准备进入休眠前，触发 Core Animation 的 Observer。这个 Observer 会触发 `CATransaction::commit()`，这是真正开始渲染流程的起点。 | 工人准备休息睡觉前，Core Animation 的"闹钟"响了，说"该开始渲染了！" |
| **T3** | **CATransaction Commit - Layout 阶段** | App 进程（主线程 CPU） | 遍历所有被标记为 `needsLayout` 的视图，调用每个视图的 `layoutSubviews` 方法，计算和更新子视图的 frame、bounds 等布局属性。Auto Layout 约束计算也在这个阶段完成。 | 先确定每个视图的位置和大小，就像装修前先量尺寸、画图纸。 |
| **T4** | **CATransaction Commit - Display 阶段** | App 进程（主线程 CPU） | **仅当覆写了 drawRect: 时才会执行**。系统创建 `CGContext`（Backing Store），执行 `drawRect:` 中的绘制代码，生成位图并设置为 `CALayer` 的 `contents` 属性。**如果没有覆写 drawRect:：** 系统会直接使用 Layer 的 `contents`（如 UIImage、backgroundColor 等），跳过 CPU 绘制流程。 | 只有当你自定义了 `drawRect:`，系统才会在这里执行你的绘制代码。如果没有自定义，就像直接用现成的图片或颜色，直接跳过这一步。 |
| **T5** | **CATransaction Commit - Prepare 阶段** | App 进程（主线程 CPU） | **性能瓶颈的关键阶段**。图片解码（仅当有图片时）、图片格式转换（仅当有图片时）、计算每个 Layer 的变换矩阵、构建渲染树（Render Tree）。**优化建议：** 图片应该提前在后台线程解码，避免在 Commit 阶段阻塞主线程。 | 这是最累的一步，就像把所有材料准备好。图片解码最容易卡，就像解压一个大文件。 |
| **T6** | **CATransaction Commit - Commit 阶段** | App 进程 → Render Server（IPC） | 将所有渲染数据打包并发送给渲染服务器进程（backboardd）。通过 IPC（进程间通信）发送数据。**为什么需要渲染服务器：** 渲染服务器是一个独立的进程，即使 App 崩溃，渲染服务器仍然可以继续工作，保证界面不会卡死。 | 把准备好的"渲染清单"和所有图片打包，通过"快递"发送给另一个专门负责渲染的"工厂"。 |
| **T7** | **Render Server 接收并解析** | Render Server 进程（backboardd） | 接收 App 进程发送过来的渲染数据，反序列化数据，解析 Layer 树和渲染指令。**关键点：** Render Server 本身并不直接做大量的"像素计算"，它主要是拆解打包发来的指令，然后调用 OpenGL/Metal API 给 GPU 发送 Draw Calls。 | 渲染工厂收到快递，拆包看看里面有什么。它不直接画画，而是把"渲染清单"翻译成 GPU 能理解的指令。 |
| **T8** | **GPU - 纹理上传** | GPU（显存） | 将 CPU 内存中的位图数据通过 PCIe 总线传输到 GPU 的显存中。位图在 GPU 中作为纹理（texture）存储。如果纹理很大，这一步也会耗时。 | 把图片从 CPU 的内存搬到 GPU 的"专用仓库"（显存）里。 |
| **T9** | **GPU - 顶点处理** | GPU（顶点着色器） | GPU 的顶点着色器处理每个 Layer 的顶点数据，应用变换矩阵（位置、旋转、缩放、透视等），计算每个顶点在屏幕空间中的最终位置。 | GPU 计算每个视图的四个角（顶点）在屏幕上的最终位置。 |
| **T10** | **GPU - 光栅化** | GPU（光栅化单元） | 光栅化将处理后的顶点数据转换为像素片段（fragments），确定哪些像素被几何图形覆盖，为每个像素片段生成插值后的属性。 | 把几何图形转换成一个个像素点，确定哪些像素被这个图形覆盖。 |
| **T11** | **GPU - 片段着色** | GPU（片段着色器） | GPU 的片段着色器对每个像素片段进行着色，应用纹理采样、颜色混合、透明度计算等，输出每个像素的最终颜色值。 | 给每个像素点"上色"，决定每个像素应该是什么颜色。 |
| **T12** | **GPU - 合成与离屏渲染** | GPU（合成单元） | 按照 Layer 的层级关系将所有 Layer 合成到一起，处理透明度混合、混合模式等。**离屏渲染（Offscreen Rendering）：** 如果 Layer 需要特殊处理（如圆角 `cornerRadius`、阴影 `shadow`、遮罩 `mask`），GPU 会先渲染到离屏缓冲区，然后再合成到主缓冲区。这会增加性能开销，应该尽量避免。 | 把所有视图按照层级关系叠在一起。如果某个视图需要特殊效果，GPU 会先在一个"临时画布"上画好，再叠到主画布上，这比较慢。 |
| **T13** | **GPU - 写入帧缓冲** | GPU（帧缓冲区） | 将合成后的最终图像写入帧缓冲（Frame Buffer）。iOS 使用双缓冲或三缓冲机制：一个 Front Buffer（正在显示）、一个或多个 Back Buffer（正在渲染）。帧缓冲区位于 GPU 显存中，大小 = 屏幕分辨率 × 4 字节（RGBA）。 | 把最终画好的完整画面存到一个"准备区"（Back Buffer）。系统有两个缓冲区，一个正在显示，一个正在准备下一帧。 |
| **T14** | **等待 VSync 信号** | 硬件（显示器） | VSync（Vertical Synchronization）是显示器硬件发出的同步信号。对于 60Hz 的显示器，VSync 信号每 16.67ms（1/60 秒）发出一次。**掉帧机制：** 如果 CPU + GPU 执行的总时间超过了 16.67ms，当 VSync 信号到来时，新的一帧还没写进 Back Buffer，交换就不会发生。此时屏幕会继续显示上一帧的内容，这在视觉上就是掉帧（Jank）。**跳帧补偿：** 系统不会补偿错过的帧。被错过的帧会被直接丢弃，App 表现为直接"跳"到最新的状态。 | 等待显示器的"换帧信号"。如果新画面还没准备好，就继续显示旧画面（掉帧）。如果错过了这一班，就等下一班，不会补偿。 |
| **T15** | **交换缓冲区（Swap）** | 硬件（显示控制器） | 当 VSync 信号到来且新帧已准备好时，交换前后帧缓冲区。交换是硬件操作，非常快速（通常只需要修改指针）。**双缓冲机制：** 避免画面撕裂（Tearing），保证画面完整显示。**ProMotion 动态 VSync：** 在现代 ProMotion 屏幕（120Hz）上，VSync 的间隔是动态的（从 10Hz 到 120Hz 变化）。 | 交换前后缓冲区，避免画面撕裂。 |
| **T16** | **扫描输出** | 硬件（显示器） | 显示器从帧缓冲区逐行扫描像素数据，从 Front Buffer 中读取每个像素的 RGB 值，将数字信号转换为模拟信号，驱动显示器的像素点。 | 显示器逐行扫描像素数据。 |
| **T17** | **像素显示** | 硬件（显示器） | 显示器的每个像素点根据接收到的 RGB 值发光，用户看到最终的画面。整个过程完成，从调用 `setNeedsDisplay` 到像素显示，通常需要 1-2 个 VSync 周期（16.67-33.34ms）。 | 像素点最终显示在屏幕上。 |

## 关键要点总结

### 1. CATransaction 的四个阶段

CATransaction Commit 分为四个阶段：

- **Layout：** 调用 `layoutSubviews` 更新布局
- **Display：** 调用 `drawRect:` 进行绘制（仅当覆写时）
- **Prepare：** 图片解码（仅当有图片时）、格式转换（仅当有图片时）、构建渲染树（性能瓶颈）
- **Commit：** 打包数据并发送给 Render Server

### 2. drawRect: 的触发条件与内存代价

**只有覆写了 `drawRect:` 方法时，系统才会走 CPU 绘制流程。** 绝大多数情况下（如设置 `backgroundColor` 或 `UIImageView` 加载图片），是不走 `drawRect:` 的。

一旦覆写 `drawRect:`，系统会为该 View 申请一块巨大的内存（寄宿图 Backing Store），其大小 = width × height × contentsScale² × 4 字节。这是极其耗费内存的，专家级优化通常建议**尽量避免覆写 drawRect:**。

### 3. 图片解码是性能瓶颈（仅当有图片时）

在 Prepare 阶段，如果 Layer 的 `contents` 是压缩图片（JPEG、PNG），CPU 必须将图片解压成位图。这一步在主线程执行，如果图片很大或未预解码，会严重卡顿主线程，导致掉帧。这是掉帧的头号杀手。

**重要理解：** 不是所有 UI 都需要图片。纯色背景（`backgroundColor`）、文字（`UILabel`）、简单几何图形等，GPU 可以直接渲染，不需要图片。只有使用 `UIImage`、覆写 `drawRect:` 或离屏渲染时才需要图片/位图。

**优化建议：** 图片应该提前在后台线程解码，避免在 Commit 阶段阻塞主线程。

### 4. VSync 与掉帧机制

如果 CPU + GPU 执行的总时间超过了 16.67ms，当 VSync 信号到来时，新的一帧还没写进 Back Buffer，交换（Swap）就不会发生。此时屏幕会继续显示上一帧的内容，这在视觉上就是掉帧（Jank）。

**跳帧补偿：** 系统不会补偿错过的帧。VSync 是硬件发出的脉冲，如果没赶上这一班，就只能等下一班。被错过的帧会被直接丢弃，App 表现为直接"跳"到最新的状态。
